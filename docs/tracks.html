Build plans

What we build for each track we enter

Manufact: the front door, on their stack

Enter
  1. Move the seller's MCP server onto mcp-use's Python server, or deploy our FastMCP server on Manufact Cloud if it accepts one. Either way: a public HTTPS URL with OAuth. ChatGPT only mounts remote servers.
  2. Ship the tool design that wins E1 (structured offers vs. free-text negotiate). The negotiation ID travels as a tool argument; the current MCP spec has no session header.
  3. One MCP App widget: a deal card for the person behind the buying agent, with what's included, price, savings vs. list, and approve and pay.
  4. Test as a remote connector in Claude and ChatGPT.
  5. Pipe session replay into the learning loop.
Proof
E1 completion and tool-error numbers, E4 zero violations, a live run in Claude.
Risk
Unverified whether Manufact Cloud hosts a plain FastMCP server. Fallback: port to mcp-use's Python server, same tool code.

Armature: agent experience, measured

Enter
  1. An AX scorecard from the experiments: completion, tool errors, rounds to close, structured vs. free-text tools, agent interface vs. static page vs. JSON feed, behavior across buyer models.
  2. Armature Evals against the deployed URL: five goal cases scored 0–5 by their judge, run before and after each tool change. No SDK needed.
  3. Armature MCP Analytics on the live server: every real session judged Succeeded / Partial / Failed. It adds a telemetry field to each tool, so we A/B it against E1 first.
  4. Self-onboarding files (/.well-known/ucp, agent card) as part of the agent experience. These are open standards, not an Armature product.
  5. Tool descriptions rewritten from E1's failure modes.
  6. What the agent sees: annotated traces of a real buying agent going from need to paid order.
  7. Ask Armature to switch on Evals for our workspace (they enable it per workspace on request).
Proof
The experiment numbers. Here the experiments are the submission.
Risk
Low. Mostly packaging plus one round of tool polish.

Stripe: checkout with controls on both sides

Enter
  1. pay_deal(deal_id, spt): the buyer agent sends a Shared Payment Token capped at the agreed total; we charge it with a PaymentIntent in test mode. The deal locks before the token exists.
  2. Fallback: a Checkout Session with a custom amount. That puts a human on a hosted page, which is weaker for this track.
  3. Show both controls refusing: the seller won't go below its floor, and payment fails above the buyer's cap.
Proof
A real test-mode payment ID for a negotiated price, plus E4's red-team numbers.
Risk
Shared Payment Tokens are a preview API. Check access first; the fallback is a Checkout Session with a custom amount.

Needed from us: a Stripe test-mode secret key set as an environment variable, and a check that the token preview works on our account.
